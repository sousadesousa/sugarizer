## 2. Jappy: "Cannot read properties of undefined (reading 'split')"

**Cause.** In `activities/Jappy.activity/js/codeeditor.js` (RapydScript output), `check_load(error, metadata, data)` restores the saved files when there is `data`, but the next block `if (len(window.files) > 0) { tag.title = list(parsed_data)[0]; editor.setValue(window.files[tag.title]) }` ran also without data. A new instance has an empty datastore entry (`data` is null) and `window.files` already holds the default "untitled" document, so `window.files[undefined]` was passed to `editor.setValue()`, and CodeMirror's `splitLinesAuto(undefined)` called `.split`. Reproduced with a Playwright script (stack: `check_load` -> `setValue` -> `splitLinesAuto`).

**Fix.** `if (data && len(window.files) > 0)`. The file says "generated, do not edit"; its source (RapydScript/riot tag) is not in this repo, so the same change should be made upstream. Removed Jappy from `knownFailures` in `test/e2e/activities.spec.js`.

**Verified:** the Jappy activity test passes (before: failed as expected); lint green; full suite below.

## 3. Flaky `lastoneloses.spec.js` "shared game: the guest"

**Cause.** The test itself is deterministic (the network is faked and it waits on conditions); the flake is in the shared `createUser` helper (`test/e2e/helpers.js`, used by 19 tests): (a) `page.locator("#next-btn").click().catch(...)`: `click()` has no timeout of its own, so when the button is replaced between the "is home visible" check and the click, it waits for the whole test timeout and the `.catch` never runs; (b) the first-screen tutorial was waited for with a 10 s `waitFor` that swallowed its failure and then the home tutorial was checked after a blind 500 ms, so an overlay appearing later covered the page; (c) 800 ms blind sleeps between steps. Reproduced outside the test runner: 6 users created in parallel with a 4x CPU throttle (CDP `Emulation.setCPUThrottlingRate`) all hung with the old helper; at 1x it never failed.

**Fix.** `createUser` now: decides from local storage whether the first-screen tutorial is expected (it starts only without user history) and waits for it to appear and disappear; clicks Next with an explicit timeout and, after each click, waits for the visible `#loginscreen_*` step to change or the home icon to exist (no sleeps); waits up to 1 s for the home tutorial and for it to be gone. The two remaining `waitForTimeout` calls (lines ~272 and ~445 of the spec) are negative checks ("nothing changes") in other tests and were left.

**Verified:** same throttled script with the new helper: 6 of 6 ok at 4x, 12 of 12 ok at 8x. `--repeat-each=20` of the guest test: 20/20 passed with `--workers=2`, and 20/20 with `--workers=8`. The flake did not reproduce at all in the test runner on this machine even before the fix (20/20 before, and 120/120 for the whole file at 6 workers), so the proof of the cause is the throttled reproduction above, not a before/after of the test. Side effect: `createUser` is about 2.5 s slower (it now waits for the home tutorial to show instead of checking after 500 ms, which often missed it).

## 4. Electron navigation guards

**What the app does.** Windows only show `file://` pages (index.html, activities); the Sugarizer server is never navigated to: the pages call it with axios (XHR) and WebSocket (presence). So the allow list is "file:// inside the app folder"; no server URL is needed. `window.open()` is used for the contributors link (http), QRCode activity (user text), and `window.open('', '_self')` (shutdown hack).

**Change.** New `navigation.js` (plain Node, no Electron import): `isAppUrl(url, appPath)` (parses the URL, must be `file:`, host-less, and the resolved path must be the app folder or inside it: `..`, `%2e%2e`, a sibling folder with the same prefix and UNC-like `file://host/...` are refused), `isExternalUrl(url)` (http/https only), `guardWindow(webContents, appPath, openExternal)`. `main.js` calls it on the main window: `will-navigate` and `will-redirect` are cancelled unless `isAppUrl`; `setWindowOpenHandler` always returns `{action: "deny"}` and calls `shell.openExternal` first for http(s) URLs only.

**Settings checked (main.js `webPreferences`):** `contextIsolation: true`, `nodeIntegration: false`, `webSecurity: true` were already set. `sandbox` was not set: it is the default `true` since Electron 20 (the app uses Electron 44 / builder `electronVersion` 41) because nodeIntegration is off, so I made it explicit with `sandbox: true`. This is safe: `preload.js` only uses `contextBridge` and `ipcRenderer`, both available in sandboxed preloads. `webviewTag` is not enabled (default off). Not changed: the guard applies to the main window only, not to subframes (`will-frame-navigate`) because some activities may embed remote content in iframes; and not to the devtools window that `--sdebug` creates (it loads `devtools://`).
**IPC note (not changed):** the `ipcMain` handlers (`save-file-dialog` with `arg.directory`/`arg.filename`, `create-tempfile`) trust the renderer, and `LoadFile` crashes on a read error (`data` undefined). Worth a separate pass.

**Tests.** `test/e2e/navigation.spec.js` (4 tests, run by `npm run test:e2e`, no browser needed) covers the allow/deny list (including traversal and non-file schemes) and `guardWindow` with a fake `webContents`. **Could not run:** Electron itself (the binary is not installed: `npm ci --ignore-scripts`; no display), so `main.js` is only syntax-checked (`node --check`) and the real events/handlers are untested.
